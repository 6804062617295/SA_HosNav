# SRS DRAFT 0.4 (Finale)

## 1. INTRODUCTION

### 1.1 Purpose
Develop a Hospital Queue Management and Indoor Navigation System for Outpatient Departments (OPD) to facilitate receiving and tracking queue numbers, as well as navigating patients to service points within the hospital. The system is developed as a prototype that can be used and demonstrated via Web Applications, focusing on Queue Management and Indoor Navigation.

### 1.2 Scope
This project is developed as a prototype to simulate the outpatient service process. It consists of 2 main parts:
1. **Patient PWA**: For patients, used for receiving and tracking queues, and utilizing the indoor navigation system.
2. **Staff Website**: For staff, used for managing and calling queues, as well as managing system-related data.

Both parts connect to the same Backend Service and PostgreSQL Database. The system implements Role-Based Access Control (RBAC) with roles including Patient, Staff, and Admin.

The indoor navigation system uses mock maps and a Navigation Graph, displaying routes as maps and step-by-step instructions without real-time user location tracking.

External systems such as HIS, Kiosks, and actual hardware are out of the development scope. Data or processes related to these will be simulated for testing and demonstration purposes.

### 1.3 Definitions
- **Patient PWA**: The patient-facing part of the system developed as a Progressive Web Application (PWA), accessible via web browsers and installable on device home screens.
- **Staff Website**: A web application for staff to manage queues and system-related data.
- **Backend Service**: The central processing system that provides APIs for the Patient PWA and Staff Website, and interacts with the database.
- **Queue Management Service**: The system for creating, managing, and tracking queue statuses.
- **Navigation Engine**: The system that calculates and displays routes using Navigation Graph data.
- **Queue QR**: A QR Code generated by the system used as a channel for patients to enter the queue reception process and link to the system.
- **QR Checkpoint**: A QR Code used as a location reference point for the Indoor Navigation system.
- **RBAC (Role-based Access Control)**: A mechanism that restricts access to system functions based on user roles.
- **Polling**: A mechanism where the client periodically sends requests to the backend to receive the latest status data.

## 2. GENERAL DESCRIPTION

### 2.1 System Perspective
The system consists of the following core components:
- Patient PWA
- Staff Website
- Backend Service
- PostgreSQL Database
- Navigation Engine

The system architecture is as follows:

```text
Patient PWA ──────┐
                  │
                  ▼
             Backend API
                  ▲
                  │
               PostgreSQL
                  ▲
                  │
Staff Website ────┘
```

The Patient PWA and Staff Website are separate frontends but share the same Backend Service and PostgreSQL Database.
HIS, Kiosks, and actual hardware are not directly connected to the system. Mock Data or Mock Processes will be used for system testing.

### 2.2 Actors
- **Patient**: Patients who use the Patient PWA to:
  - Log in or enter the Queue Flow
  - Receive or link a queue
  - View queue status
  - View destination information
  - Use the Indoor Navigation system
- **Staff**: Personnel who use the Staff Website to:
  - View queues
  - Call queues
  - Change queue statuses
  - Forward queues to the next service point
  - Verify information related to service provision
- **Admin**: System administrators who can manage basic system data, such as:
  - Location
  - Navigation Node
  - Navigation Edge
  - QR Checkpoint

### 2.3 Constraints
- The system is a prototype, not a production system for actual hospital deployment.
- HIS and actual hospital systems are not connected to this system.
- Kiosks and actual hardware will not be developed.
- Patient and queue data are simulated (mock data).
- The Navigation system does not have real-time user location tracking.
- The Navigation system uses predefined maps and Navigation Graphs.
- QR Codes used in the system are generated by the system for use within the prototype.

### 2.4 Assumptions
- Users can access the system via web browsers.
- Patients can use the PWA via mobile devices.
- Staff can use the Staff Website via desktop or laptop computers.
- The system has network connectivity to communicate with the Backend.
- Location and Navigation Graph data are prepared by Admins prior to use.
- Queue QRs are generated by the system for use in the queue reception or linking process.
- QR Checkpoints are installed or simulated at various points within the map.

### 2.5 Operating Environment
- **Patient PWA**: Supports modern web browsers on mobile devices that support Progressive Web Applications, such as Safari and Google Chrome.
- **Staff Website**: Supports modern web browsers on desktops or laptops, such as Google Chrome, Safari, and Microsoft Edge.
- **Backend**: The Backend Service runs on a server or cloud environment that supports Node.js.
- **Database**: Uses PostgreSQL as the primary database management system.

## 3. SYSTEM REQUIREMENTS

### 3.1 Functional Requirements
- **FR-01 (Authentication & Registration)**: The system must support login using Email and Password. The system must allow Patients to register for new accounts via the Patient PWA. However, there is no UI for registering Staff or Admin accounts; those roles are pre-provisioned directly into the database. The system must store passwords in a hashed format and must not store passwords as plain text.
- **FR-02 (Queue QR)**: The system must allow Staff or Admins to generate Queue QRs. The Staff Website must provide a section in the Dashboard where Staff can create a Queue for standard entry (e.g., triage/registration), after which the system generates a QR Code for that specific Queue. The QR Code encodes a URL pointing to the Patient PWA with a unique queue token. Each Queue QR is single-use and maps to exactly one Queue entry. When a patient scans the Queue QR, the system links the patient to that Queue and displays the queue status. Patient login is not required to scan and track a Queue. This process serves as a prototype mock of the Kiosk queue ticket workflow.
- **FR-03 (Queue Tracking)**: The system must display the patient's Queue information, including Queue Number, current status, queue order, destination or service point, and information related to waiting for service. The system must update Queue data periodically via polling to ensure the information displayed to the user is current.
- **FR-04 (Queue Status)**: The system must support Queue statuses, namely Waiting, Called, Processing, Completed, and Skipped. The system will not use Hold and Cancelled statuses in the prototype to limit the system scope.
- **FR-05 (Staff Queue Management)**: Staff can manage Queues via the Staff Website, including viewing the queue list, calling a queue, changing queue status, and forwarding a queue to the next service point.
- **FR-06 (Queue History)**: The system must be able to record the history of Queue status changes to track the service sequence. The history log must record at least the Queue, Status, time of status change, and the Staff who performed the action.
- **FR-07 (Indoor Navigation)**: The system must be able to display the route from a starting point to a destination within the building using Navigation Graph data. It must support indoor maps, multi-floor navigation, Navigation Nodes, Navigation Edges, QR Checkpoints, and step-by-step navigation.
- **FR-08 (Navigation Map)**: Patients can view the building map and the route to a specified destination. The map uses predefined mock data and does not track the user's location in real-time.
- **FR-09 (Step-by-Step Navigation)**: The system must provide step-by-step travel instructions, such as go straight, turn left, turn right, and proceed to the destination. Users can click 'Next Step' to view the subsequent instruction.
- **FR-10 (QR Checkpoint)**: The system must support QR Checkpoints linked to Navigation Nodes, used as reference points for the navigation process and separated from Queue QRs.
- **FR-11 (Admin Map Management)**: Admins can manage Navigation data via CRUD operations, including Locations, Navigation Nodes, Navigation Edges, and QR Checkpoints.
- **FR-12 (Access Control)**: The system must restrict access to functions based on user roles (Patient, Staff, Admin). The Backend must verify permissions before allowing access to resources.
- **FR-13 (Notification)**: The system must notify queue changes via the Patient PWA using internal web application mechanisms, such as visual notifications, popups, badges, and queue status updates. Native push notifications are excluded.

### 3.2 Interface Requirements
- Design the UI according to Usability and Universal Design principles (easy-to-read text, appropriate button sizes, clear queue statuses).
- The Patient PWA and Staff Website are separate frontends but use the same Backend API.

### 3.3 Performance Requirements
- The system must respond to general user operations within approximately 3 seconds.
- Queue Tracking uses polling to periodically update data.

### 3.4 Database Requirements
- **User**: `user_id`, `email`, `password_hash`, `name`, `role`
- **Queue**: `queue_id`, `patient_id`, `destination_id`, `status`, `created_at`
- **QueueHistory**: `history_id`, `queue_id`, `status`, `updated_at`, `staff_id`
- **Location**: `location_id`, `name`, `building`, `floor`
- **NavigationNode**: `node_id`, `location_id`, `type`
- **NavigationEdge**: `edge_id`, `from_node`, `to_node`, `instruction`
- **QRCheckpoint**: `qr_id`, `node_id`

### 3.5 Security Requirements
- **Authentication**: Passwords are hashed, with expiring Session/Token.
- **Authorization**: Role verification is performed every time.
- **Transport Security**: HTTPS/TLS.
- **Input Validation**: Check and validate inputs sent by the client.
- **Secrets**: Stored via Environment Variables.

### 3.6 Quality Attributes
- **Usability**: Easy to use, does not require a manual.
- **Maintainability**: Clear separation of Frontend, Backend, and Database.
- **Availability**: No production SLA requirements as this is a prototype.

### 3.7 Prototype Mocks & Limitations
- **External Systems**: No HIS, Kiosks, or actual hardware.
- **Queue**: Uses mock data and Queue QRs.
- **Navigation**: Uses mock maps; no GPS, real-time tracking, compass, or AR.
- **Notification**: Uses notifications within the Web Application.
